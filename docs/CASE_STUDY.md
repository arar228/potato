# Night Arcade — инженерный кейс

[← Репозиторий и запуск](../README.md)

## Задача

Собрать Telegram Mini App, в котором мобильный интерфейс, авторизация, игровой баланс
и история операций образуют одну систему. Ключевой инженерный вопрос — как провести
пользовательское действие через API и БД так, чтобы повтор запроса сохранял исходный
результат, а итоговый баланс соответствовал журналу операций.

Проект использует внутренние игровые очки и представляет функциональный прототип.
Этот кейс описывает проверяемые решения в исходном коде; сведения о коммерческом масштабе,
количестве пользователей, составе команды и роли конкретного участника здесь не заявляются.

## Решение 1. Граница доверия проходит через API

Клиент отправляет исходный Telegram `initData` в заголовке авторизации. API пересчитывает
HMAC, сравнивает подпись через `timingSafeEqual`, проверяет время и валидирует подписанный
объект пользователя. Идентичность для защищённых маршрутов берётся из результата этой проверки.

Практическая ценность — единый источник пользовательской идентичности для баланса,
игр, истории и proof раундов. Общие Zod-схемы дополнительно задают контракт обеим сторонам.

Код: [проверка initData](../apps/api/src/modules/auth/telegram-init-data.ts),
[auth plugin](../apps/api/src/plugins/auth.plugin.ts),
[контракты](../packages/shared/src/index.ts).

## Решение 2. Баланс и журнал обновляются вместе

`Wallet.balance` — снимок для быстрого чтения. `LedgerEntry` хранит историю изменений.
Первый вход объединяет пользователя, wallet и стартовое начисление в одну serializable-транзакцию.

Игровой раунд проходит следующие шаги внутри транзакции:

1. Поиск уже обработанного `Idempotency-Key`.
2. Проверка игры и условное списание при достаточном балансе.
3. Получение seed, вычисление исхода и запись раунда.
4. Запись списания в ledger и начисления при выигрышном исходе.
5. Раскрытие seed завершённого раунда и возврат результата.

На уровне PostgreSQL заданы ограничения неотрицательного баланса, уникальные ключи
идемпотентности и триггер append-only для журнала. В игровых операциях и Daily Reward
конфликт сериализации `P2034` повторяется максимум три раза.

Компромисс: serializable делает требования к целостности явными, но под конкуренцией
нужны измерения конфликтов, задержек и повторов. Текущие unit-тесты подменяют Prisma,
поэтому реальные блокировки и PostgreSQL-триггеры должны проверяться отдельно.
Защита журнала описывает обычные операции приложения; это не криптографическая
неизменяемость данных против администратора БД.

Код: [UserService](../apps/api/src/modules/users/user.service.ts),
[GamesService](../apps/api/src/modules/games/games.service.ts),
[DailyRewardService](../apps/api/src/modules/daily-reward/daily-reward.service.ts),
[миграция](../apps/api/prisma/migrations/20260829000000_foundation/migration.sql).

## Решение 3. Сетевой повтор имеет явную семантику

Мобильное соединение может оборваться после выполнения серверной операции. Клиент
передаёт `Idempotency-Key`; сервер сохраняет связь ключа с раундом или наградой и при
повторе возвращает сохранённый результат. Принадлежность результата проверяется по пользователю.

Клиент выполняет один повтор сетевого `TypeError` для GET или запроса с ключом
идемпотентности. Отдельный unit-тест проверяет повтор Coin Flip и стабильную траекторию
Pocket Pool при повторном запросе.

Следующий шаг — интеграционные проверки двух одновременно поступивших запросов и
переиспользования одного ключа с изменённым payload. Текущая реализация не хранит
отдельный fingerprint payload, поэтому этот контракт требует явного развития.

Код: [API-клиент](../apps/web/src/lib/api-client.ts),
[тесты игрового сервиса](../apps/api/test/games.service.test.ts).

## Решение 4. Результат отделён от анимации

Pocket Pool вычисляет исход на API. Браузер получает исход, целевую лузу и seed траектории,
после чего Canvas / Matter.js воспроизводит визуальную сцену. Повтор одного раунда
воспроизводит те же параметры траектории.

Так интерфейс можно развивать отдельно от расчёта результата. Физика здесь —
представление серверного исхода, а не самостоятельный симулятор соревновательного бильярда.

Код: [PoolPhysicsCanvas](../apps/web/src/features/games/PoolPhysicsCanvas.tsx),
[серверный расчёт](../apps/api/src/modules/games/games.service.ts).

## Решение 5. Пользователь может пересчитать proof

Для Coin Flip и Pocket Pool есть серверный seed, его SHA-256 hash и HMAC-SHA256 от
`clientSeed + ":" + nonce`. В текущем потоке `clientSeed` берётся из ключа идемпотентности.
После раунда сервер раскрывает seed. Браузер через Web Crypto проверяет hash,
числовое значение и соответствие результата правилам игры.

**Граница доказательства:** verifier подтверждает внутреннюю согласованность данных,
которые получил от сервера. Он не сопоставляет proof с отдельным commitment, заранее
сохранённым клиентом. Сервер также может создать seed во время обработки раунда,
если открытый seed ещё не существует. Поэтому полный протокол доказуемой честности
против недоверенного сервера этой версией не подтверждён.

Следующий шаг — явная привязка запроса к `commitmentId`, хранение ожидаемого hash
на клиенте и тесты подмены / повторного использования commitment.

Код: [FairnessService](../apps/api/src/modules/fairness/fairness.service.ts),
[browser verifier](../apps/web/src/features/fairness/verify-fairness.ts).

## Проверка воспроизводимости

Проверка документационного обновления: **6 сентября 2026**, Windows x64,
Node.js **22.17.0**, pnpm **11.19.0**. Исходный runtime-коммит:
[`8e7e7ce`](https://github.com/arar228/potato/commit/8e7e7ce3fed6ed061e7b098977764d806565007e).

Команды из корня:

```powershell
pnpm install --frozen-lockfile
pnpm db:generate
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

Все шесть команд завершились успешно: frozen install, генерация Prisma Client,
проверка типов, lint, **20 unit-тестов** (18 API + 2 web) и сборка shared / API / web.
Lockfile и runtime-код сохранены. У `packages/shared` собственных тестов пока нет;
его test-скрипт допускает пустой набор.

Действующий Telegram-бот, PostgreSQL, Redis и production-развёртывание этой проверкой
не затрагивались. Сквозной запуск приложения и Docker-сборка в её объём не входили.

Область unit-тестов: Telegram HMAC и свежесть, начальное начисление, wallet / ledger,
Coin Flip, Pocket Pool, идемпотентный повтор, Daily Reward и backend / browser verifier.
Prisma в сервисных тестах заменена in-memory объектами. Автоматического CI workflow
в исходном runtime-коммите нет.

## Что нужно для следующего эксплуатационного этапа

1. **Интеграционная целостность:** PostgreSQL в тестовом окружении, конкурентные
   списания / начисления, отказ транзакции и проверка append-only триггера.
2. **Воспроизводимая поставка:** CI для frozen install, types, lint, tests и build;
   отдельная Linux/Docker-матрица. Сейчас workspace выбирает только `win32/x64`.
3. **Полный Telegram-сценарий:** отдельный тестовый бот, HTTPS-окружение, mobile E2E,
   проверка восстановления после сетевого обрыва.
4. **Эксплуатационная готовность:** DB readiness, логи с редактированием чувствительных
   данных, проверка восстановления бэкапа и внешние health-пробы. `/health` сейчас
   отвечает о процессе; текущий rate limit хранится в памяти одного процесса.
5. **Развитие продукта:** провайдер ежедневных заданий, связанный commitment-протокол
   и реальный PvP. Сейчас Daily Freebie в production блокируется флагом `DAILY_TASK`,
   а PvP использует Arcade Bot.

Порядок выбран вокруг целостности данных и воспроизводимости: эти свойства дают основу
для последующего расширения игровых сценариев и измерения производительности.
